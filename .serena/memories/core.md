# AnVề — Project Core

Monorepo for AnVề: an Android (Jetpack Compose) client backed by a Go HTTP
API and PostgreSQL/PostGIS. Modular monorepo per ADR 0001 (`docs/adr/`):
one repo, one pinned toolchain, but each app keeps its own build system and
its own CI workflow. Phase: M0–M4 implemented. M4 is automated-verified but
pending runtime/device validation; M3 has a runtime HTTP smoke test but is NOT
field-validated on a device (battery/background/OEM); M5+ planned. Engineering
session state lives in `docs/implementation/progress.md` — read it first when
resuming work.

## Source map

- `apps/server` — Go module `github.com/QuocDuong16/anve/server`.
  - `cmd/api`, `cmd/migrate` — thin entrypoints only; business logic belongs in `internal/`.
  - `internal/httpapi` — chi router. Surface includes health/meta, M1 auth, M2 Circle, M3 location ingestion and M4 audience/latest-location APIs; `RequireAuth` verifies sessions per request and business routes 503 without a database.
  - `internal/auth` — M1 domain: opaque sessions (SHA-256 hashes only), Google ID-token verification (`google.golang.org/api/idtoken`), PG store with transactional audit; location consent uses `location_sharing_version` compare-and-set, incremented atomically with the consent and audit transaction; `internal/auth/authtest` holds the in-memory store fake shared by tests.
  - `internal/audit` — privacy event recorder; `audit_log` has NO FK to users by design (survives account deletion).
  - `internal/circles` — M2 domain: circles/memberships/invites; authorization enforced AT THE STORE (membership checked before any read: outsider→404, member-without-owner-role→403); one-circle-per-user unique index is the MVP invariant; invite redeem is atomic (FOR UPDATE, single winner); owner leaving a populated circle requires dissolve=true (cascades).
  - `internal/config` — env-based config. `LISTEN_ADDR` defaults to `127.0.0.1:<PORT>` in development and is mandatory in every other environment (fail closed). Refuses `AUTH_DEV_LOGIN_ENABLED` unless `ENVIRONMENT` is exactly `development`; a non-loopback listener additionally needs `AUTH_DEV_LOGIN_ALLOW_NETWORK=true` plus a non-catch-all `AUTH_DEV_LOGIN_ALLOWED_CIDRS`.
  - `internal/httpapi` also installs `RequireDevNetwork` on the dev-login route: it checks `RemoteAddr` against the configured prefixes and never trusts `X-Forwarded-For`/`X-Real-IP`. An empty allowlist denies every request; a blocked source gets 403 `DEV_LOGIN_NETWORK_DENIED`.
  - `internal/locations` — M3 domain: batch validation (ranges/NaN/timestamp/bounds), transactional authorization (user FOR SHARE → session/device FOR SHARE → membership FOR SHARE), idempotent insert with unique (user_id,event_id), atomic batch semantics, retention purge. Contract codes: LOCATION_BATCH_INVALID/TOO_LARGE, LOCATION_EVENT_TOO_OLD, LOCATION_CONSENT_REQUIRED, LOCATION_CIRCLE_REQUIRED, DEVICE_NOT_AUTHORIZED, LOCATION_TEMPORARILY_UNAVAILABLE.
- `apps/android` — app `com.anve.app`; `data/` (api Retrofit+Moshi, auth token storage, `data/location` Room queue + WorkManager sync) + `tracking/` (provider, adaptive policy, coordinator, foreground service, metrics) + `ui/` grouped by feature (`splash`, `signin`, `home`, `circle`, `tracking`, `theme`); `AppContainer` is the manual DI root.
- `packages/api-contracts/openapi.yaml` — the HTTP contract; single source of truth for the API surface.
- M4 reads use `internal/locationaccess`: temporal Circle membership periods, fresh sharing epochs and explicit owner-to-viewer grants. M3 points without an epoch stay unreadable. Latest reads enforce authorization in PostgreSQL; Android uses foreground HTTPS conditional polling with ETags, no persistent location cache, and no inferred source-device offline status.
- `infra/docker/docker-compose.yml` — local stack (postgres/postgis, one-shot `migrate`, `api`); always runs with the repo root as project directory so `.env` and relative paths work the same locally and in CI. EVERY published port is loopback-only: postgres `127.0.0.1:$POSTGRES_PORT` and API `127.0.0.1:$API_PORT`. The API container sets `LISTEN_ADDR=0.0.0.0:8080` (it must accept the port mapping) and the `edge` bridge is pinned to `172.28.0.0/24` so the dev-login source allowlist can name it. Postgres uses a dedicated, otherwise-empty `db-host` bridge network: Docker does not forward published ports for containers whose only network is `internal: true`, so without it `localhost:5432` silently refuses connections.
- `infra/migrations` — ordered SQL migrations applied by the custom migrator in `apps/server/cmd/migrate` (not golang-migrate). The migrator owns `schema_migrations` (created in `ensureBookkeepingTable`) and serializes runs with a `pg_advisory_lock`; business migrations must never create or drop the bookkeeping table — `0001_extensions.down.sql` is a deliberate no-op for that reason. `0004_locations` adds `location_points` (PostGIS geography, unique (user_id,event_id), user/device/capture-time/GIST indexes, FK cascade to users/devices). Integration tests for the migrator live in `apps/server/cmd/migrate` (skipped without `TEST_DATABASE_URL`; need a PostGIS-capable server).
- `docs/adr` — accepted architecture decisions.
- `scripts/` — toolchain drift check (`check_toolchain_versions.sh`), Dependabot schema validation (`check_dependabot.py`) and Compose exposure validation (`check_compose_ports.py`, Make target `compose-lint`, also a CI repository job): fails if any Compose port is published beyond loopback.

## Invariants

- Contract-first: change `packages/api-contracts/openapi.yaml` before changing handlers.
- `mise.toml` + `mise.lock` are the single source of truth for the Go release, JDK and Gradle distribution; versions that appear in more than one file are guarded by the drift check.
- The API server still starts without a database (`DATABASE_URL` optional), but since M1 `readyz` fails and business routes answer a structured 503 in that state.
- Auth invariants (M1, ADR 0002; hardened in ADR 0004): sessions are opaque tokens stored as SHA-256 hashes and verified against the DB on EVERY request (immediate revocation); one active session per device (re-login supersedes); refresh rotates BOTH tokens atomically (FOR UPDATE, single winner); `users.location_sharing_enabled` defaults to FALSE and is the consent switch every location feature must respect; `location_sharing_version` is the monotonic CAS boundary, and consent changes increment it in the same transaction as their audit row; the dev login (`POST /api/v1/auth/dev-login`) is mounted only when `ENVIRONMENT=development` and never mounted otherwise. It is also network-restricted (ADR 0005): loopback listener by default; non-loopback needs explicit opt-in + CIDR allowlist; the route checks the real source address and denies with 403 `DEV_LOGIN_NETWORK_DENIED`; catch-all CIDRs refuse startup; no shared secret is embedded in the app/repo. Dev and Google identities are ISOLATED: neither sign-in path may enter the other's email-matched account (409 `IDENTITY_CONFLICT`).
- Audit ownership (ADR 0004): every business mutation records exactly ONE audit row from inside its transaction (stores own it; services carry no recorder; no best-effort path). Failed/refused operations write no audit row.
- Account deletion (ADR 0004, amended by ADR 0005 §4): `DELETE /api/v1/me` must refuse with 409 `CIRCLE_HAS_MEMBERS` when the caller owns a circle with other members; only explicit dissolve ends a populated circle. Empty owned circles are removed in the same transaction with `circle.dissolved` (detail `via=account_deletion`). Deletion locks the USER row `FOR UPDATE` FIRST, then owned circles: every circle creation holds a FK `KEY SHARE` on that user row, so creation either commits first (and the scan/count sees it) or fails its FK after deletion. This closes the race where a newly created circle was cascaded before any member count/audit. Deletion retries on PG `40P01`/`40001`; `LeaveCircle`/`RedeemInvite` retry too. `internal/auth/export_test.go` exposes a test-only barrier after the user lock; the concurrency tests use observed `pg_stat_activity` lock waits instead of sleeps.
- Android session lifecycle (ADR 0004/0005/0006): navigation follows session storage only; a failed `/me` is offline, never signed out. Deletion clears local storage only after 2xx. Session sign-out clears locally and queues a bounded Keystore-sealed `pending_revocations` record (max 8, 7 days, no account PII) for best-effort retry. Consent changes use a separate owner-scoped encrypted DataStore outbox with one latest operation per account (operation id, desired state, server version, generation, retry state, expiry); it survives session clear and is never inherited by another account. If OFF precedes offline sign-out, its narrow refresh credential is sealed separately for at most 7 days and session revocation waits for server-confirmed OFF. Expiry/rejected credentials leave an explicit owner-auth-required operation, never a false confirmation. `ConsentMutationCoordinator` serializes durable local mutations and upload/request admission, but does not hold a lock over network I/O. The server CAS version orders mutations across devices/processes.
- Android session storage is DataStore sealed with an Android Keystore AES-GCM key (never plaintext); the DataStore file also holds the pending revocation. `SessionInterceptor` does one rotation-aware refresh-retry on 401; Google client id lives in gitignored `values/config_local.xml` (placeholder in `values/config.xml`); debug builds default `API_BASE_URL` to `http://10.0.2.2:8080` (cleartext allowlist for 10.0.2.2/localhost only). Retrofit rejects `@Body` on `@DELETE`, so `deleteMe` uses `@HTTP(method="DELETE", hasBody=true)` (latent runtime bug found in the hardening pass).
- Device identity is an APP INSTALLATION identity: stable across restarts/updates/sign-out, new after reinstall/factory reset; no hardware identifier is read. The server keys `devices` on (user, client_device_id) and treats it accordingly.
- `middleware.RealIP` is deliberately not used in the router (X-Forwarded-For spoofing); a trusted-proxy allowlist is a deployment-time concern.
- The dev database is published on loopback only; production deployments keep the database on an internal network with no published port.

M3 location invariants (ADR 0006):
- Ingestion is one atomic batch (1–200 events, 512 KiB), authenticated only by the session. The body's `clientDeviceId` must equal the session's device. User id never comes from the body.
- Authorization is inside the write transaction: `users FOR SHARE` (consent + account deletion serialization) → `sessions JOIN devices FOR SHARE` (sign-out/device revocation) → membership `FOR SHARE` (Circle leave). No consent cache. A revoked session/device or account that commits first is invisible to the batch; a batch that locks first commits and is then cascaded by the revocation.
- Idempotency is `(user_id, event_id)` + `ON CONFLICT DO NOTHING`; duplicates are reported, not inserted. `recorded_at` is preserved; `received_at` is server time. Future >2m rejected; capture older than retention rejected.
- Retention: `LOCATION_RETENTION_DAYS` (default 30, 1–365) measured from capture time; purge runs at startup and hourly.
- Android: `TrackingManager` (motion IDLE/STATIONARY/MOVING/JOURNEY and operational ACTIVE/DEGRADED/OFFLINE/PAUSED) only reports `activelyTracking` when service and provider run. FGS is `location`, `START_NOT_STICKY`, notification + stop action, no BOOT_COMPLETED; process death surfaces recovery intent rather than auto-restarting. Permission flow is staged: API 28 has no background runtime grant; API 29 requests it only after foreground; API 30+ explains the need, opens supported app Settings, and rereads OS permission on resume without automatic reprompt.
- Consent OFF is local-first: synchronously close process-wide location/upload admission, invalidate starts and stop provider callbacks/service before storage; persist the owner-scoped outbox and legacy flag, purge the unsent Room queue, then request server CAS. Storage failure keeps the process gate closed but is not a durable guarantee after process death if all writes fail. Purge/service-stop failures remain explicit; queued points are never uploaded while blocked. A batch admitted before OFF may already be in flight; backend row locks order ingestion and revocation. A consent 409 is read-only reconciliation: matching state updates the snapshot without a duplicate write/audit; differing state/version is stored as conflict and parked, never automatically rebased. A fresh explicit owner action creates a new operation against the latest known version. Account changes never execute another owner's operation, and stale responses cannot replace newer local generations. The legacy global `pending_consent_revocation` flag is migrated into this outbox.
- Room queue is owner-scoped, eventId PK, max 5,000 / 7 days, exported schema v1, no destructive migration, not app-level encrypted (documented threat model in ADR 0006 §6). WorkManager uses unique network-constrained sync, 100 events per normal batch and a 64-request total pass budget. Client prevalidation removes only invalid rows; atomic validation failures use bounded batch isolation and only an isolated permanently invalid singleton may be dropped. Accepted/duplicate acknowledgements alone delete successful rows; transport/429/5xx retry with stable event ids; unknown permanent errors preserve the queue; consent/device/circle refusal follows the explicit privacy stop/purge policy.
- Android backup/transfer rules exclude `sharedpref`, `database` AND `file/datastore` (Preferences DataStore lives in files/datastore, not sharedpref — this is where the sealed session blob and installation id are) in both `backup_rules.xml` (API < 31) and `data_extraction_rules.xml` (API 31+, cloud backup and device transfer). The Room database (`database` domain) stays out of both backup and device transfer; this is the per-file policy for M3. Room is not additionally encrypted at the application layer in M3 (private storage + OS FDE + backup exclusion + 7-day local retention; residual-risk decision in ADR 0006 §6).

M4 read authorization is implemented from ADR 0007: explicit owner→viewer grants are bounded by Circle membership periods and owner sharing epochs. Current membership alone never grants historical points; existing M3 points receive no grants by default. PostgreSQL enforces grants in the latest-location read query; revocation changes the authorized ETag and subsequent reads deny access. Android uses foreground conditional HTTPS polling (not WebSocket/SSE), Maps Compose, and no persistent location cache. M4 is automated-verified but still pending runtime/device validation. Android audience mutations distinguish confirmed, rejected and unknown outcomes; unknown mutations are never replayed and trigger an owner-bound authoritative re-read. Sharing generations reject stale responses, and mutations are single-flight per owner/viewer.

## Product documentation

The product scope, status taxonomy (Implemented / Verified / Planned /
Proposed / Not in scope) and milestone plan live in `docs/product/`
(`overview.md`, `features.md`, `user-journeys.md`, `privacy-and-safety.md`,
`roadmap.md`, `glossary.md`, `non-functional-requirements.md`) and
`docs/architecture/overview.md`. These are the source of truth for product
intent — check them before developing a feature, and update them when feature
scope changes. Do not assume planned functionality is implemented: M0–M4 are implemented
(automated-verified; M3 has runtime HTTP smoke evidence but still awaits
on-device field validation for battery/background/OEM behavior; M4 still awaits
map/runtime validation). M5+ History/Places, M6 SOS/FCM, and M7 Journey remain
planned. M4 Live Map uses conditional polling rather than server push. AGENTS.md
has a "Product context & source of truth" section pointing to the same documents.
